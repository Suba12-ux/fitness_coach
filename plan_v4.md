# Plan 4 — Настройка CI/CD и Production Deployment для AI Fitness Coach

## 1. Цель

Настроить автоматическую сборку, публикацию Docker-образов и развёртывание AI Fitness Coach на удалённом сервере через GitHub Actions.

**Целевой сценарий:**

1. Разработчик отправляет изменения в ветку `main`.
2. GitHub Actions запускает тесты Backend и Frontend.
3. При успешном прохождении тестов собираются Docker-образы.
4. Образы публикуются в приватный Docker Hub.
5. GitHub Actions подключается к серверу по SSH.
6. На сервере скачиваются новые образы и обновляется приложение.
7. После развёртывания выполняются проверки работоспособности.

Первоначальный доступ к приложению — по публичному IP-адресу сервера и порту `8081`. Домен и HTTPS будут настроены отдельным этапом позднее.

---

## 2. Архитектура развёртывания

### Сервисы приложения

Сохранить существующую архитектуру проекта:

| Сервис | Назначение | Docker-образ |
|---|---|---|
| postgres | PostgreSQL 16 | Официальный |
| redis | Redis 7 | Официальный |
| migrate | Alembic migrations | sensei-backend |
| backend | FastAPI | sensei-backend |
| worker | ARQ Worker | sensei-backend |
| frontend | Nginx + React SPA | sensei-frontend |

Используются два собственных Docker-образа:

- `sensei-backend` — собирается из корня репозитория с использованием `backend/Dockerfile`.
- `sensei-frontend` — собирается с использованием `frontend/Dockerfile`.

Важно: Backend, Worker и Migrate используют один и тот же Backend-образ.

### Публикация портов

Для первоначального запуска:

- Frontend: внешний порт `8081` → внутренний порт Nginx `80`.
- Backend, PostgreSQL и Redis не должны быть доступны напрямую из публичной сети.
- Frontend должен проксировать API-запросы к Backend через внутреннюю Docker-сеть.

Публикация Frontend должна позволять открывать приложение по адресу:

`http://SERVER_IP:8081`

Не использовать порты `80` и `443`, поскольку на сервере уже работает другое приложение.

## 3. Этап 1. Аудит существующего проекта

Перед изменениями агент должен изучить:

- `docker-compose.yml`
- `backend/Dockerfile`
- `frontend/Dockerfile`
- `frontend/nginx.conf`
- `.env.example`
- `.gitignore`
- конфигурацию Alembic
- существующие тесты Backend и Frontend
- настройки GitHub Actions, если они уже существуют.

Проверить:

1. Корректность сборки обоих Docker-образов.
2. Наличие healthcheck у необходимых сервисов.
3. Правильность зависимостей между `postgres`, `redis`, `migrate`, `backend`, `worker` и `frontend`.
4. Корректность порядка запуска миграций.
5. Наличие постоянных Docker volumes для PostgreSQL и Redis.
6. Отсутствие секретов внутри Docker-образов.
7. Корректность проксирования API через Frontend Nginx.

Не переписывать рабочую архитектуру без необходимости.

Если обнаружены проблемы, сначала исправить их и проверить локальный запуск.

## 4. Этап 2. Production Docker Compose

Создать отдельный файл:

`docker-compose.production.yml`

Требования:

- Использовать готовые образы из Docker Hub вместо локальной сборки.
- Не выполнять сборку Docker-образов на сервере.
- Использовать переменные окружения из серверного `.env`.
- Сохранить PostgreSQL и Redis в постоянных Docker volumes.
- Не публиковать PostgreSQL и Redis во внешнюю сеть.
- Не публиковать Backend напрямую во внешнюю сеть.
- Открыть Frontend через порт `8081`.
- Сохранить внутреннюю Docker-сеть между сервисами.

### Миграции

Сервис `migrate` должен:

- Запускать `alembic upgrade head`.
- Выполняться до запуска Backend и Worker.
- Завершаться с ненулевым кодом при ошибке миграции.

Backend и Worker должны запускаться только после успешного завершения миграций.

Использовать Docker Compose dependency condition `service_completed_successfully`, если это поддерживается текущей конфигурацией Compose.

### Образы

Использовать переменные:

- `DOCKERHUB_USERNAME`
- `IMAGE_TAG`

Пример имён:

- `${DOCKERHUB_USERNAME}/sensei-backend:${IMAGE_TAG}`
- `${DOCKERHUB_USERNAME}/sensei-frontend:${IMAGE_TAG}`

Тег должен соответствовать Git commit SHA. Дополнительно можно публиковать тег `latest`.

## 5. Этап 3. GitHub Actions — CI

Создать workflow:

`.github/workflows/ci-cd.yml`

На первом этапе настроить автоматическую проверку проекта.

Триггер:

- `push` в ветку `main`;
- `pull_request` в ветку `main` — только CI, без публикации образов и развёртывания.

### Backend

Выполнить:

1. Установку Python 3.12.
2. Установку зависимостей из `backend/requirements.txt`.
3. Запуск тестов через `pytest -q`.

### Frontend

Выполнить:

1. Установку Node.js 22.
2. Установку npm-зависимостей с использованием lock-файла.
3. Запуск `npm test`.
4. Запуск `npm run build`.

Все проверки должны завершиться успешно до начала сборки и публикации Docker-образов.

Если в проекте отсутствуют необходимые тестовые скрипты или конфигурации, не обходить проблему искусственным успешным завершением. Зафиксировать её и предложить корректное исправление.

---

## 6. Этап 4. Сборка и публикация Docker-образов

После успешного CI при push в `main`:

1. Выполнить авторизацию в Docker Hub.
2. Собрать Backend-образ.
3. Собрать Frontend-образ.
4. Присвоить обоим образам тег Git commit SHA.
5. Дополнительно присвоить тег `latest`.
6. Отправить образы в приватный Docker Hub.

Учитывать особенности сборки:

- Backend build context — корень репозитория.
- Backend Dockerfile — `backend/Dockerfile`.
- Frontend Dockerfile — `frontend/Dockerfile`.

Использовать GitHub Actions cache для ускорения повторных сборок.

Не передавать `.env`, API-ключи и другие секреты в Docker build context или build arguments.

---

## 7. Этап 5. CD — автоматическое развёртывание

После успешной публикации образов GitHub Actions должен подключиться к серверу по SSH.

На сервере предполагается следующая структура:

```text
/opt/sensei/
├── docker-compose.production.yml
└── .env
```

Сервер должен быть предварительно подготовлен:

- установлен Docker Engine;
- установлен Docker Compose plugin;
- создан каталог `/opt/sensei`;
- размещены production Compose и `.env`;
- настроен доступ к приватным Docker Hub-образам.

### Последовательность деплоя

1. Подключиться к серверу по SSH.
2. Перейти в `/opt/sensei`.
3. Авторизоваться в Docker Hub (если авторизация не настроена заранее).
4. Получить актуальные образы по тегу Git commit SHA.
5. Запустить обновление через Docker Compose:

```bash
docker compose -f docker-compose.production.yml pull

docker compose -f docker-compose.production.yml up -d
```

6. Дождаться запуска необходимых сервисов.
7. Проверить состояние контейнеров.
8. Выполнить HTTP-проверки `/health` и `/ready`.
9. Если проверка не пройдена — завершить GitHub Actions с ошибкой и вывести диагностические логи.

Важно: не использовать `docker compose down -v`. Нельзя удалять постоянные volumes с данными PostgreSQL и Redis.

## 8. Этап 6. Безопасность и GitHub Secrets

Добавить следующие GitHub Repository Secrets:

| Secret | Назначение |
|---|---|
| `DOCKERHUB_USERNAME` | Имя пользователя Docker Hub |
| `DOCKERHUB_TOKEN` | Токен доступа Docker Hub |
| `SERVER_HOST` | IP-адрес сервера |
| `SERVER_USER` | Пользователь SSH |
| `SERVER_SSH_KEY` | Приватный SSH-ключ |

Дополнительные требования:

- Не хранить SSH-ключи и пароли в репозитории.
- Не записывать секреты в логи GitHub Actions.
- Использовать отдельный Docker Hub Access Token.
- По возможности использовать отдельного пользователя сервера для деплоя.
- Ограничить SSH-доступ необходимыми правами.
- Не передавать содержимое `.env` через GitHub Actions.
- Не помещать `.env` в Git.

### Серверный `.env`

Файл создаётся и заполняется вручную на сервере.

Использовать `.env.example` как основу.

Проверить обязательные параметры:

- `APP_ENV`
- `DATABASE_URL`
- `REDIS_URL`
- `AUTH_COOKIE_SECURE`
- `LLM_PROVIDER`
- `DEEPSEEK_API_KEY`
- остальные настройки приложения.

**Важное замечание по HTTP:** при `APP_ENV=production` приложение автоматически включает `Secure` для авторизационной cookie. Обычный HTTP-доступ по IP не обеспечивает передачу такой cookie браузером. Для временного тестирования без HTTPS потребуется явно отключить `AUTH_COOKIE_SECURE` (`false`). Это допустимо только как временное исключение для тестового запуска. После настройки HTTPS вернуть `true`.

## 9. Этап 7. Откат (Rollback)

Предусмотреть возможность вернуться к предыдущей версии приложения.

Требования:

- Использовать неизменяемые Docker-теги с Git commit SHA.
- Не полагаться исключительно на `latest`.
- Сохранять возможность указать предыдущий `IMAGE_TAG` в production Compose.
- Документировать ручной откат через изменение тега и повторный запуск Compose.

Не выполнять автоматический откат миграций базы данных. Миграции должны быть совместимыми с предыдущей версией приложения, насколько это возможно.

## 11. Критерии завершения

Работа считается завершённой, когда:

- [ ] Существующий локальный Docker Compose продолжает работать.
- [ ] Создан `docker-compose.production.yml`.
- [ ] Production-конфигурация использует готовые Docker-образы.
- [ ] PostgreSQL и Redis сохраняют данные между перезапусками.
- [ ] Миграции выполняются до запуска Backend и Worker.
- [ ] Настроен CI для Backend и Frontend.
- [ ] При успешном CI собираются оба Docker-образа.
- [ ] Образы публикуются в приватный Docker Hub.
- [ ] Настроен SSH-деплой на сервер.
- [ ] При push в `main` приложение автоматически обновляется.
- [ ] Приложение доступно по `http://SERVER_IP:8081`.
- [ ] Работают регистрация, авторизация и создание тренировочного плана.
- [ ] Работают проверки `/health` и `/ready`.
- [ ] Ошибки деплоя корректно отражаются в GitHub Actions.
- [ ] Реализована возможность отката на предыдущую версию.
- [ ] Создана документация по развёртыванию.

## 12. Ограничения

В рамках этой задачи:

- Не покупать и не настраивать домен.
- Не настраивать HTTPS и Let's Encrypt.
- Не изменять существующее приложение на сервере.
- Не занимать порты `80` и `443`.
- Не удалять данные PostgreSQL или Redis.
- Не переносить существующую инфраструктуру сервера.
- Не добавлять Kubernetes и другие избыточные инструменты.
- Не менять бизнес-логику AI Fitness Coach без необходимости для деплоя.

После завершения агент должен предоставить отчёт:

1. Какие файлы созданы и изменены.
2. Какие проверки выполнены.
3. Как устроен CI/CD.
4. Какие GitHub Secrets необходимо добавить.
5. Что нужно вручную сделать на сервере.
6. Какие действия остаются за пользователем для первого запуска.
7. Какие ограничения или проблемы остались.
