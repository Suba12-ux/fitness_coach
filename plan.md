# План разработки мультиагентного AI Fitness Coach — версия 3

## 1. Цель этапа

Развить существующий прототип мультиагентной системы до полноценного backend-приложения с:

- интеграцией с DeepSeek API;
- архитектурой с несколькими специализированными агентами;
- централизованной оркестрацией через Supervisor;
- PostgreSQL для постоянного хранения данных;
- Redis для очередей и координации фоновых задач;
- отдельным Worker для выполнения длительных задач;
- FastAPI в качестве HTTP API;
- Docker и Docker Compose для запуска всей инфраструктуры;
- полноценной документацией в корневом `README.md`;
- возможностью запуска как с Docker, так и без него.

**Главный принцип:** версия 3 является продолжением существующего проекта. Перед изменениями необходимо изучить текущую реализацию, сохранить рабочие компоненты и постепенно расширять архитектуру. Не переписывать проект с нуля без технической необходимости.

## 3. Целевая архитектура версии 3

Система должна состоять из следующих основных компонентов:

1. **FastAPI Backend** — принимает запросы от клиента, управляет API и создаёт задачи.
2. **Supervisor** — анализирует запрос, формирует план и управляет выполнением агентов.
3. **Специализированные агенты** — выполняют отдельные задачи.
4. **DeepSeek API** — основная языковая модель для интеллектуальной обработки запросов.
5. **PostgreSQL** — постоянное хранение пользователей, запусков процессов, состояний и результатов.
6. **Redis** — брокер очередей и инфраструктура для фонового выполнения.
7. **Worker** — отдельный процесс, который получает задачи из очереди и выполняет workflow.

### Общая схема

```text
              FRONTEND
                  |
                  v
             FASTAPI
                  |
                  v
              REDIS
                  |
                  v
               WORKER
                  |
                  v
              SUPERVISOR
                  |
          +-------+-------+
          |               |
          v               v
       LLM API         AGENTS
      DeepSeek       +---------+
          |          | Profile |
          |          | Training|
          |          | Safety  |
          |          +---------+
          |               |
          +-------+-------+
                  |
                  v
              POSTGRES
```

Схема является логическим представлением. Конкретные зависимости и порядок вызовов определяются реализацией workflow.

## 5. Развитие системы агентов и Supervisor

### Supervisor

Supervisor — центральный управляющий компонент системы.

Его обязанности:

1. Получить пользовательский запрос.
2. Передать запрос модели для анализа.
3. Получить структурированный план выполнения `TaskPlan`.
4. Проверить корректность плана.
5. Определить необходимые задачи и зависимости.
6. Запустить подходящих агентов.
7. Контролировать выполнение.
8. Обрабатывать ошибки и повторные попытки.
9. Проверять и объединять результаты.
10. Сформировать итоговый ответ.

LLM может предлагать план, но не должна самостоятельно определять неограниченный набор действий. Supervisor обязан проверять разрешённые типы задач и зависимости.

### Схемы

Сохранить и развивать существующие:

- `AgentTask`;
- `AgentResult`;
- `TaskPlan`;
- `TaskSpec`;
- `PlanState`.

Структурированные ответы модели должны проходить Pydantic-валидацию.

### Специализированные агенты

Сохранить существующие:

- `ProfileAgent`;
- `TrainingAgent`.

Также сохранить программный `SafetyChecker`.

В дальнейшем архитектура должна позволять добавлять новые агенты без необходимости переписывать Supervisor.

Примеры возможных будущих агентов:

- NutritionAgent;
- ProgressAgent;
- RecoveryAgent;
- RecommendationAgent.

Добавление этих агентов не является обязательной частью текущего этапа.

### Параллельное выполнение

Независимые задачи должны выполняться параллельно там, где это безопасно и оправдано.

В предыдущем прототипе для этого использовался `asyncio.gather`. В версии 3 необходимо сохранить эту возможность, но учитывать, что длительные workflow будут исполняться Worker, а не HTTP-процессом.

### Надёжность выполнения

Предусмотреть:

- тайм-ауты;
- ограниченные повторные попытки;
- обработку исключений;
- защиту от повторного выполнения одной задачи;
- контроль зависимостей между задачами;
- сохранение промежуточного состояния;
- понятные статусы выполнения.

Повторные попытки должны учитывать тип ошибки: не все ошибки можно исправить повторным запросом.

Сохранить программную проверку безопасности из предыдущей версии.

SafetyChecker не должен зависеть исключительно от решений LLM.

Это учебный программный компонент, а не медицинская диагностика. Для реального продукта потребуется отдельная экспертная проверка рекомендаций и сценариев риска.

## 8. Redis и фоновые задачи

### Задача

Вынести длительное выполнение workflow из HTTP-запросов в отдельную очередь.

Backend должен принимать запрос и ставить задачу на выполнение. Worker должен самостоятельно получать её и выполнять.

### Выбор технологии

Рассмотреть Celery и ARQ.

Выбрать одну технологию и обосновать выбор с учётом:

- асинхронной архитектуры;
- сложности настройки;
- повторных попыток;
- мониторинга;
- интеграции с Redis;
- удобства тестирования.

Не подключать обе системы одновременно без конкретной необходимости.

### Требования

- Redis как брокер очередей.
- Отдельный Worker-процесс.
- Постановка workflow в очередь.
- Обработка ошибок выполнения.
- Ограничение повторных попыток.
- Контроль повторной доставки задач.
- Сохранение прогресса в PostgreSQL.
- Возможность восстановить статус после перезапуска Worker.

### Статусы workflow

Предусмотреть как минимум:

- `queued`;
- `running`;
- `completed`;
- `failed`;
- `cancelled`;
- `needs_info`.

Статус и актуальное состояние должны сохраняться в PostgreSQL. Redis не должен становиться единственным хранилищем результатов и состояния workflow.

### Проверка этапа

- Backend ставит задачу в очередь.
- Worker получает и выполняет её.
- Результат сохраняется в PostgreSQL.
- Клиент может получить статус выполнения.
- При перезапуске Worker состояние процесса не теряется.
- Повторная доставка задачи не приводит к неконтролируемому дублированию результата.

## 9. FastAPI

Сохранить существующее API и расширить его для фонового выполнения.

### Основные endpoints

#### `POST /workflow`

- принимает пользовательский запрос;
- валидирует входные данные;
- создаёт запись workflow в PostgreSQL;
- ставит задачу в очередь;
- возвращает ID запуска и начальный статус.

#### `GET /workflow/{id}`

Возвращает:

- ID;
- статус;
- прогресс, если он предусмотрен;
- текущий этап;
- результат, если выполнение завершено;
- информацию об ошибке, если выполнение завершилось неудачно.

#### `GET /health`

Проверяет доступность приложения.

При необходимости добавить отдельный readiness endpoint для проверки зависимостей: PostgreSQL и Redis.

### Требования

- Pydantic-схемы запросов и ответов.
- Корректные HTTP-коды.
- Обработка ошибок.
- Валидация ID.
- Отсутствие внутренних traceback и секретов в публичных ответах.

## 10. Docker и Docker Compose

Весь проект должен запускаться через Docker Compose.

### Обязательные отдельные сервисы

| Сервис | Назначение |
|---|---|
| `backend` | FastAPI |
| `worker` | Выполнение фоновых задач и агентов |
| `postgres` | Основная база данных |
| `redis` | Очереди и координация |

Backend и Worker могут использовать один Dockerfile, но должны запускаться как отдельные контейнеры с разными командами.

### Требования

- Dockerfile для приложения.
- `docker-compose.yml`.
- Отдельные сервисы для всех четырёх компонентов.
- Внутренняя Docker-сеть.
- Переменные окружения.
- `.env.example`.
- Постоянный volume для PostgreSQL.
- Healthcheck для инфраструктурных сервисов.
- Корректный порядок готовности зависимостей.
- Отдельная команда для миграций.
- Логи контейнеров.
- Возможность перезапуска сервисов.

### Команды запуска

Документация должна содержать проверенные команды:

```bash
docker compose up --build
```

Остановка:

```bash
docker compose down
```

Просмотр логов:

```bash
docker compose logs -f
```

Не удалять данные базы при обычной остановке. Отдельно предупредить, что `docker compose down -v` удаляет volumes и может привести к потере данных.

- некорректный ответ LLM;
- падение Worker;
- повторная доставка задачи;
- повторный запуск workflow.

Для автоматических тестов не требовать настоящего DeepSeek API key. Основные сценарии должны работать с MockLLMProvider.

### Команды проверки

```bash
pytest -q
```

Дополнительно провести ручную проверку полного процесса:

1. Запустить инфраструктуру.
2. Отправить запрос в API.
3. Убедиться, что workflow появился в PostgreSQL.
4. Убедиться, что задача попала в Redis.
5. Убедиться, что Worker выполнил задачу.
6. Проверить итоговый статус.
7. Получить результат через API.

## 19. Правила разработки

1. Перед изменением файла изучить его текущую реализацию.
2. Не переписывать работающий код без обоснования.
3. Не удалять существующие тесты — расширять их.
4. Каждый этап завершать запуском тестов.
5. Не смешивать бизнес-логику, работу с БД и HTTP-слой.
6. Не давать LLM неограниченный доступ к действиям приложения.
7. Не хранить секреты в коде.
8. Все длительные задачи выполнять через Worker.
9. PostgreSQL использовать как источник постоянного состояния.
10. Документацию обновлять по фактической реализации.

**Итоговая цель:** получить расширяемый мультиагентный backend AI Fitness Coach, который использует DeepSeek, управляет агентами через Supervisor, хранит состояние в PostgreSQL, выполняет фоновые задачи через Redis и Worker и полностью запускается как локально, так и через Docker Compose.
